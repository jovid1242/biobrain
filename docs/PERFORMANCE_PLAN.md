# PERFORMANCE PLAN — что тормозит и что с этим делать

Основано на измерениях Milestone 2: `results/milestone2/experiments/profile.json` (таймеры фаз шага),
`results/milestone2/benchmarks/*.jsonl`, `results/milestone2/benchmarks/aggregation_microbench.json`.
Никакой backend в M2 не переписывался. Решение о следующем шаге принимает владелец.

## 1. Где уходит время (NumPy, Apple M5, float32, 500 шагов)

Доля времени цикла по фазам, три самые большие:

| подграф | вход | time-step | event-driven (sparse) | event-driven (auto) |
|---|---|---|---|---|
| 1k | 0.01 % | порог 29 %, синапт. вход 14 %, рефрактерность 14 % | агрегация 34 %, утечка 31 %, сброс/планирование 20 % | утечка 34 %, агрегация 27 %, сброс/планирование 20 % |
| 1k | 1 % | gather исходящих 43 %, доставка (bincount) 24 % | агрегация 45 %, утечка 32 % | утечка 58 %, сброс/планирование 14 % |
| 10k | 0.01 % | доставка 32 %, gather 23 %, порог 20 % | агрегация 42 %, утечка 32 % | утечка 44 %, агрегация 25 % |
| 10k | 1 % | gather 48 %, доставка 40 % | агрегация 66 %, утечка 22 % | утечка 63 %, агрегация 13 % |
| 10k | 10 % | gather 54 %, доставка 41 % | **агрегация 83 %** | утечка 42 %, агрегация 26 %, планирование 22 % |

«Утечка» в event-driven — это ленивый пересчёт `v·α^k`: несколько gather и scatter по массивам состояния
затронутых нейронов. «Агрегация» — группировка пришедших событий по нейрону.

## 2. Выводы из измерений

1. **В time-step доминируют синапсы, а не нейроны.** При входе от 0.1 % до 10 % на выборку исходящих рёбер и
   доставку событий уходит 54 → 81 % времени на 1k и 73 → 94 % на 10k. Операции по всем N нейронам (утечка,
   порог, рефрактерность) при входе ≥ 1 % занимают ≤ 17 % на 1k и ≤ 8 % на 10k. Поэтому пропуск обновлений нейронов, главное преимущество event-driven, экономит мало: число
   синаптических операций в обоих режимах одинаково.
2. **Event-driven в NumPy платит за разреженность дважды.** Группировка событий делается сортировкой
   (`np.unique`, O(E log E) с большой константой), а утечка — случайными gather/scatter по памяти. По
   микробенчмарку плотный `bincount` быстрее сортировки при E ≥ N/5 (при N ≥ 10k сортировка ещё выигрывает при
   E ≤ N/10; при N = 1k плотный быстрее уже с E = N/10).
3. **При очень низкой активности всё решают накладные расходы интерпретатора.** Шаг time-step на 10k нейронов
   занимает ~7 мкс, event-driven ~9 мкс. Оба почти целиком состоят из вызовов Python/NumPy.
4. **Итог для этой реализации.** Event-driven быстрее только при ≲ 0.015–0.12 события на нейрон за шаг, то есть
   когда пропускается ≳ 93–99 % обновлений (перелом на 100 нейронах — при 94–96 %, на 1k–10k — при 97.5–98.6 %).
   На 50k перелома нет ни при каком входе. Это не свойство event-driven подхода вообще, а свойство
   «NumPy + плотные подграфы».

## 3. Что изменил бы компилируемый backend (гипотезы — не измерено)

| узкое место | в NumPy | в компилируемом коде (ожидание) |
|---|---|---|
| группировка событий | сортировка O(E log E) | O(E): накопитель по нейрону + список затронутых, без сортировки |
| ленивая утечка | несколько временных массивов на шаг | один проход по затронутым нейронам, без аллокаций |
| накладные расходы | ~15 вызовов NumPy на шаг, мкс каждый | ~0 |
| time-step | векторные операции уже в C | выигрыш меньше; SIMD возможен |

Ожидание (гипотеза): в компилируемом коде точка перелома сдвинется к существенно более высокой активности,
потому что стоимость event-driven станет ≈ c₁·события + c₂·затронутые нейроны, без сортировки и аллокаций.
Проверить можно только измерением на той же модели и тех же входах, с тем же тестом эквивалентности.

## 4. Варианты и рекомендация

| вариант | трудозатраты | риск | что даст |
|---|---|---|---|
| **Numba** (JIT для обоих режимов на CPU) | низкие: те же массивы, та же модель | нужна установка пакета (**требует одобрения владельца**) | быстрый ответ на вопрос «перелом — артефакт NumPy?» |
| C++ / Rust расширение | средние | сборка, поддержка | максимальный контроль на CPU |
| Swift | средние | отдельный стек | естественно для macOS; повторно использовать SiliconFly нельзя (другая модель) |
| Metal (GPU) | высокие | передача памяти CPU↔GPU, разреженный control flow плохо ложится на GPU | хорош для плотного time-step на больших N, не для разреженного event-driven |

**Рекомендация.** Перед Milestone 3 не переписывать движок целиком. Сделать один маленький замер: Numba-версии
обоих режимов на 1k/10k/50k с тем же тестом эквивалентности и той же матрицей активности. Если перелом
сдвигается заметно, компилируемый CPU-backend становится основой. Metal рассматривать только для плотного
time-step на полном мозге и только после этого замера. Установка Numba — решение владельца.

## 5. Milestone 2.5: что показала компиляция (измерено)

Numba (CPU, один поток), изолированная матрица 1k/10k/50k × 6 уровней входа × 4 backend × 3 seed,
`results/milestone25/`. Подробно — `docs/MILESTONE25_REPORT.md`.

1. **Компиляция ускорила оба режима, event-driven сильнее.**
   - time-step: в 1.3–11 раз;
   - event-driven: в 5–53 раза.

   Время NumPy-прогонов воспроизвело M2 (медиана отношения 0.996).
2. **Перелом сдвинулся к более высокой активности, но не до реалистичной.**

   | подграф | вход в точке перелома | событий на нейрон за шаг | пропущено обновлений |
   |---|---|---|---|
   | 1k | 0.0056 % → 0.16 % | 0.028 → 0.39 | 98 % → 72 % |
   | 10k | 0.0014 % → 0.048 % | 0.015 → 0.43 | 99 % → 69 % |
   | 50k | нет → нет | — | — |

   При входе 0.1–1 % compiled event-driven примерно вдвое медленнее compiled time-step на 10k и 50k (исход C
   по правилу из плана).
3. **Узкое место после компиляции — доставка синаптических событий** (случайный доступ к накопителям целей),
   одинаковая по объёму в обоих режимах. Модель стоимости по изолированным прогонам: time-step ≈ 0.56 нс на
   нейрон + 0.69 нс на событие; event-driven ≈ 1.96 нс на обновлённый нейрон + 1.17 нс на событие. Медианная
   ошибка 10 % и 16 %.
4. **Предел выигрыша любой event-driven реализации на CPU при этой связности.** Даже если обновление нейронов
   стоит 0, события всё равно доставляются. Максимальное преимущество ≈ 1 + (0.56 · N) / (0.69 · E) (оценка по
   модели). При 1 % входа E/N ≈ 2.5–3.1, откуда предел ≈ 1.3×. При 0.1 % на 10k — ≈ 1.8× по модели и до 2.9× по
   профилю (1 / доля доставки в compiled time-step). На 50k и полном мозге — 1.1–1.9×.
5. **Детали реализации важны для event-driven.** Ядро с ветвлениями тратило 12–16 нс на обновление нейрона,
   без ветвлений — 2–3 нс при той же арифметике.

**Вывод для выбора backend.** Дальнейшая оптимизация event-driven на CPU при реалистичной активности может дать
не больше ~1.3–1.8× даже в идеале. Главная стоимость — события, а не нейроны. Решение о следующем шаге —
в отчёте M2.5.
