## ENVIRONMENT

  вентилятора; все бенчмарки M2.5 шли **от сети** (заряд 45–64 %). В 276 записях `pmset -g therm` не сообщил ни
  одного температурного предупреждения. Температуры без root недоступны.
- **Python 3.14.6, NumPy 2.5.3, Numba 0.67.0, llvmlite 0.49.0.** Numba установлена `pip` в основной `.venv`
  (wheels cp314 macOS arm64 с PyPI; numba требует numpy < 2.6). `pip freeze` до и после отличается только
  numba и llvmlite. Версии закреплены в `requirements.lock`, extra `compiled` — в `pyproject.toml`.
  Отдельное окружение не понадобилось.
- **Компиляция:** один поток, `parallel=False`, `fastmath=False`, кэш на диске. LLVM определяет процессор как
  `apple-m4` — llvmlite 0.49 не знает M5.
- Загрузка ядер из кэша в новом процессе ≈ 47 мс. Она не входит в замеренное время.
- **Энергия** не измерялась. `powermetrics` требует `sudo` и не запускался. Если владелец захочет измерить,
  можно в отдельном терминале запустить `sudo powermetrics --samplers cpu_power -i 500` на время прогона. Это
  мощность всего SoC-пакета, а не процесса.

## IMPLEMENTATION

- **`compiled.py`:** ядра time-step и event-driven на Numba. Порядок арифметики тот же, что у NumPy:
  - в time-step синаптический вход суммируется по нейрону в float64 в порядке событий и приводится к типу один раз;
  - в event-driven та же ленивая утечка по таблице α^k; спайки шага сортируются по возрастанию без выделения
    памяти, чтобы порядок сумм совпадал.
- **Без выделений в цикле.** Счётчики аллокаций Numba не зависят от числа шагов: 18 на прогон TS и 31 на прогон
  ED при 50 и при 800 шагах.
- **Варианты накопления в event-driven** (`touched`, `dense`, `copy`) сравнивались по правилу, записанному до
  исследования. Выбран `touched`: накопитель + список впервые затронутых целей + обход CSR от id спайков в момент
  доставки. Геометрическое среднее времени: 9.75 мс против 15.2 у `dense` и 11.9 у `copy`.
- **Первая версия ядер с ветвлениями** тратила 12–16 нс на обновление нейрона в ED. Версия без ветвлений с той же
  арифметикой — 2–3 нс. Обе версии проверены, результаты первой сохранены (`*_v1_branchy.json`). Time-step
  ускорился от этой замены лишь на 10–15 %.
- **Инфраструктура:** backend и вариант — отдельные поля записи. `config_hash` у NumPy и compiled одного режима
  одинаков во всех 108 парах. Пустой процесс: NumPy 90 MiB, Numba 155 MiB. Порядок 216 прогонов матрицы
  перемешан с фиксированным seed.
- NumPy-движок M2 не менялся. Добавился только выбор backend в `engine.run`.

### Модель стоимости и предел выигрыша event-driven

Подгонка по изолированным прогонам (МНК по относительной ошибке, неотрицательные члены; эмпирика, не закон):

- compiled TS: T ≈ 0.56 нс · N + 0.69 нс · E (медианная ошибка 10 %, максимальная 41 %);
- compiled ED: T ≈ 11 нс + 1.96 нс · A + 1.17 нс · E, где A — обновлённые нейроны (медианная ошибка 16 %,
  максимальная 39 %).
- Экстраполяция с 1k–50k на полный мозг **занизила** время compiled на 35–39 % (NumPy — на 15–18 %): стоимость
  события растёт с размером сети.

**Предел для любой event-driven реализации.** Она всё равно должна доставить те же события, поэтому не может
быть быстрее фазы доставки compiled TS.
- По профилю (1 / доля доставки compiled TS): 50k — 1.06–1.89×; 10k при входе ≥ 0.1 % — 1.09–2.9×.
- По модели для полного мозга: 1.13–1.72×.
- Измеренное compiled ED на полном мозге — 0.53–0.61×.

| 10k, 0.1 % | TS | 8.7 → 5.6 (26 % → 65 %) | 24.7 → 3.0 (74 % → 35 %) |
| 10k, 0.1 % | ED | 149 → 6.3 (80 % → 50 %) | 38.2 → 6.3 (20 % → 50 %) |
| 10k, 1 % | TS | 11.0 → 6.0 (12 % → 24 %) | 79.1 → 18.7 (88 % → 76 %) |
| 10k, 1 % | ED | 412 → 18.8 (77 % → 36 %) | 126 → 33.4 (23 % → 64 %) |
| 50k, 0.1 % | TS | 34.1 → 28.9 (9 % → 25 %) | 344 → 85.9 (91 % → 75 %) |
| 50k, 0.1 % | ED | 1,608 → 93.4 (75 % → 43 %) | 541 → 125 (25 % → 57 %) |
| 50k, 1 % | TS | 40.0 → 30.0 (6 % → 15 %) | 601 → 164 (94 % → 85 %) |
| 50k, 1 % | ED | 2,231 → 125 (71 % → 36 %) | 896 → 217 (29 % → 64 %) |

- **До компиляции (подтверждение M2).**
  - В NumPy TS gather исходящих рёбер и доставка занимают 54–96 % шага при входе ≥ 0.1 %.
  - В NumPy ED ленивая утечка (gather/scatter) занимает 26–67 %, группировка событий (`np.unique`/`bincount`) —
    12–49 %.
  - На шаг приходится 24–41 вызова, видимых Python, и 11–35 операторов и индексаций у TS; 3–99 вызовов и
    10–58 операций у ED.
  - Временная память — до 44 MiB за прогон.
- **Куда сместилось узкое место:**
  - **ED:** компиляция в 16–60 раз удешевила обновление нейронов (убран Python/NumPy), но доставка на 10k и 50k
    при входе ≥ 0.1 % ускорилась лишь в 3.5–6 раз. Теперь при входе ≥ 0.1 % доставка — 50–82 % времени ED.
  - **TS:** обновление по всем N почти не ускорилось на больших сетях (NumPy уже векторизован: 1.2–1.3× на 50k при
    входе ≤ 1 %). Доставка на 50k ускорилась в 3.1–4.7 раза и остаётся главной фазой (75–95 % при входе ≥ 0.1 %).
- **Стоимость единицы после компиляции:** time-step — 0.56 нс на нейрон, event-driven — ≈ 2 нс на затронутый
  нейрон. Доставка события — 0.5–0.9 нс на 1k–10k и больше на крупных сетях.

## OBSERVED RESULTS

1. **Compiled backend корректен.** Одинаковые режимы совпадают с NumPy побитово на всех проверенных сетях
   (включая полный мозг), в обоих типах чисел, до 40,000 шагов.
2. **Компиляция ускорила time-step в 1.3–11 раз:** 3.0–3.9× на 50k и полном мозге, 4–5× на 10k, 4–11× на 1k.
   Event-driven — в 5–53 раза.
3. **После компиляции event-driven выигрывает только при очень редкой активности** на 1k и 10k: до 28× при входе
   0.001 %, 3–5× при 0.01 %. При 0.1–10 % входа он в 1.4–2 раза медленнее (исход C); исключение — 1k при 0.1 %
   (1.15×). На 50k и полном мозге он медленнее при любом входе (0.50–0.75×).
4. **Перелом сдвинулся** с ≈ 0.02 до ≈ 0.4 приходящих событий на нейрон за шаг. Требуемая доля пропущенных
   обновлений снизилась с ≈ 98 % до ≈ 70 %.
5. **Полный коннектом работает на ноутбуке:** 0.23–1.3 с на секунду модели при 268–327 MiB (compiled TS/ED).
   Сборка сети — 935 MiB.
6. **На baseline полный мозг самоподдерживает активность** (4–15 Гц), и слабый вход не делает её разреженной.
7. **Пропускная способность:** compiled TS — около 0.45–1.7 млрд событий/с, стоимость события растёт от 0.6 нс
   (1k/10k) до 1.5–1.8 нс (полный мозг).
8. **ESTIMATE M2 для полного мозга** занизил RAM на 17 %. Его модель времени NumPy ошиблась в медиане на 8 %
   (до 25 %), а сценарный расчёт — на 28 %: в M2 предполагалось 102 события на спайк, фактически 142–180.

## INTERPRETATION

- **M2 был ограничен реализацией, но не только ею.** Python/NumPy давал 3–50-кратные накладные расходы, и
  компиляция сдвинула перелом примерно в 30 раз по входу. Но при активности, которую эта модель на реальной
  проводке даёт при умеренном входе, узкое место — **синаптические события**. Их одинаково много в обоих
  режимах, а event-driven платит ещё и за учёт затронутых нейронов и ленивую утечку. Поэтому исход C.
- **Почему выгода от пропуска обновлений мала.** Обновить нейрон подряд по массиву стоит 0.56 нс, случайным
  доступом — около 2 нс. Event-driven выгоден, только если пропускается большая часть нейронов, а в плотных
  подграфах и в самоподдерживающемся полном мозге за шаг затрагивается 37–87 % нейронов.
- **Предел оптимизации event-driven на CPU при этой связности**, даже с бесплатным обновлением нейронов (оценка
  по профилю и модели): 1.1–1.9× на 50k и полном мозге, до 2.9× на 10k при входе 0.1 %. Больших выигрышей от
  дальнейшей оптимизации event-driven на CPU ждать нельзя.
- **Рост стоимости события с размером сети** (0.6 → 1.8 нс) похож на ограничение пропускной способностью и
  задержкой памяти: случайный доступ к накопителям и массивам рёбер, которые не помещаются в кэш. Это гипотеза:
  аппаратных счётчиков промахов кэша в M2.5 нет.
- **M2.5 не сравнивает BioBrain с другими архитектурами** и ничего не говорит об эффективности топологии мухи
  или об энергии. Сравнивались только способы исполнения одной модели.

## LIMITATIONS

- **Условия замеров.** Один компьютер (Apple M5, macOS 27, от сети), один поток, без аппаратных счётчиков.
  Выводы о bottleneck памяти косвенные. На другом железе (многоядерный CPU, GPU, нейроморфное) баланс может быть
  другим.
- **Реализация и её потенциал.**
  - LLVM компилирует для `apple-m4`, специфичные возможности M5 не используются.
  - Проход по нейронам в compiled TS не векторизован SIMD. Если его векторизовать, time-step ускорится и исход C
    только усилится.
  - Исследованы 3 стратегии накопления для ED, многопоточность — нет.
  - Первая версия ED с ветвлениями была в 5 раз медленнее. Возможны и более удачные реализации ED; их потолок
    ограничен оценкой выше.
- **Статистика и модели.**
  - Время на 1k при редком входе — единицы микросекунд на прогон, шум таймера велик; 3 seed.
  - Точка перелома интерполирована между уровнями входа, различающимися в 10 раз.
  - Модели стоимости линейны, ошибка до 40–60 % на отдельных прогонах, и они не экстраполируются на рост сети
    (занижение на 35–39 %).
- **Модель мозга.**
  - Все ограничения M2 остаются (`docs/M2_LIMITATIONS.md`): допущения о весах и знаках, LIF без нижней границы,
    одна задержка, калибровка по своим правилам.
  - Самоподдержание полного мозга на baseline — свойство этой модели при этом gain, а не установленное свойство
    мозга мухи.
- **Эквивалентность разных режимов в float32** на длинных горизонтах не держится (известно из M2).
- **RAM** измеряется через `ru_maxrss` и включает то, что удерживает аллокатор. Базовый процесс Numba на 65 MiB
  больше NumPy.
- **Энергия не измерялась.**

## OPEN QUESTIONS

1. Изменит ли баланс многопоточная или векторизованная (SIMD) реализация обоих режимов? Ожидание (гипотеза):
   скорее ускорит time-step.
2. Можно ли уменьшить стоимость доставки для обоих режимов переупорядочиванием нейронов и рёбер по локальности
   памяти? Это оптимизация доставки, а не выбор event-driven.
3. Как добавит работу пластичность (M3)? Обновления на событие и на синапс масштабируются с числом событий,
   которое уже доминирует.
4. Самоподдерживающаяся активность полного мозга на baseline — следствие модели (нет шума, нет нижней границы,
   delta-синапсы) или проводки? Нужен контроль null-топологиями.
5. На каком железе событийное исполнение действительно выигрывает (GPU для плотного time-step, нейроморфные
   чипы для событий)? Это аппаратный вопрос, M2.5 его не проверяет.
6. Нужно ли измерение мощности (`powermetrics`, `sudo`) — решение владельца.

## RECOMMENDATION FOR M3

**Идти в M3, ещё один CPU-backend не делать.** Основания — данные:

- **Производительности уже хватает для M3.** Compiled time-step гоняет полный коннектом за 0.23–1.3 с на секунду
  модели при ≤ 0.33 GiB, подграфы 1k–10k — в микросекундах на шаг. 1,000 с модели на полном мозге ≈ 4–22 мин.
- **Event-driven на CPU при реалистичной активности не выигрывает**, и его потолок даже в идеале — 1.1–1.9× на 50k
  и полном мозге (до 2.9× на 10k при 0.1 %).
  Дальнейшая оптимизация CPU-backend дала бы константу, а не порядок.
- **Эталон для M3:** compiled time-step (float32 для прогонов, float64 для проверок), NumPy — как независимая
  сверка. Compiled event-driven оставить для очень разреженных режимов и как второй оракул.
- **Решения владельца перед M3** (остаются из M2):
  - какие допущения фиксировать (минимум два знака глутамата);
  - dtype-политика;
  - нужна ли калибровка с другим протоколом (полный мозг на baseline самоподдерживается).
- **Пересмотреть backend** после того, как M3 определит правило пластичности и его стоимость на событие.

## Ответы на вопросы M2.5

**Q1. Во сколько раз компиляция ускорила time-step?**

| сеть | ускорение | при входе 0.1–1 % |
|---|---|---|
| 1k | 4.4–11× | 10–11× |
| 10k | 1.3–5.1× | 4.1–4.5× |
| 50k | 3.0–3.9× | 3.4–3.5× |
| 139k | 3.0–3.3× | 3.1–3.2× |

Меньше всего ускорение там, где NumPy уже векторизует проход по всем нейронам.

**Q2. Во сколько раз компиляция ускорила event-driven?**
В 5–53 раза:

| сеть | ускорение | при входе 0.1–1 % |
|---|---|---|
| 1k | 6.4–53× | 24–42× |
| 10k | 6.1–25× | 13–14× |
| 50k | 5.1–10.5× | 9.5–10.5× |
| 139k | 5.9–9.7× | 9.4–9.7× |

**Q3. После компиляции выигрывает ли event-driven у time-step?**
Только при очень редкой активности на 1k и 10k: 28× и 21× при входе 0.001 %, 4.7× и 3.0× при 0.01 %, 1.15× на
1k при 0.1 %. При реалистичной активности — нет: 0.49–0.61× (исход C). На 50k и полном мозге — ни при каком
входе (0.50–0.75×).

**Q4. При какой активности crossover?**

| сеть | вход | событий на нейрон за шаг | пропущено обновлений |
|---|---|---|---|
| 1k | ≈ 0.16 % | ≈ 0.39 | ≈ 72 % |
| 10k | ≈ 0.048 % | ≈ 0.43 | ≈ 69 % |
| 50k, 139k | нет: даже при 0.001 % входа сеть получает ≥ 1.1 события на нейрон за шаг | | |

**Q5. Меняется ли crossover с размером сети?**
В единицах входа — да: 0.16 % → 0.048 % → нет. В единицах «событий на нейрон за шаг» он примерно постоянен
(≈ 0.4 у 1k и 10k). Размер влияет через рекуррентную активность: большие подграфы и полный мозг самоподдерживают
её и никогда не опускаются ниже перелома.

**Q6. Какая синаптическая пропускная способность?**
Compiled TS — 853 млн событий/с (медиана; 445–1,666 млн), compiled ED — 475 млн/с (323–968 млн). Полный мозг:
TS 549–657, ED 323–360 млн/с. Для сравнения, NumPy TS — 222 млн/с, NumPy ED — 45 млн/с.

**Q7. Какова стоимость одного синаптического события?**

- **Compiled TS:** 1.17 нс с учётом всех затрат шага (0.60–2.25); фаза доставки — 0.84 нс (медиана профиля);
  модель — 0.69 нс на событие + 0.56 нс на нейрон.
- **Compiled ED:** 2.11 нс с учётом всех затрат (1.03–3.10); доставка — 1.21 нс; модель — 1.17 нс на событие +
  1.96 нс на обновлённый нейрон.
- **Полный мозг, compiled TS:** 1.5–1.8 нс.

**Q8. Какой bottleneck после компиляции?**
**Синаптические события:** случайный доступ при доставке к накопителям целей и массивам рёбер. Это 55–95 %
времени compiled TS при входе ≥ 1 % и 50–82 % времени compiled ED.

Второе место у ED — обновление затронутых нейронов (≈ 2 нс каждое, 18–50 %). Python/NumPy orchestration
устранён: выделений в цикле нет, один вызов ядра на прогон. Стоимость события растёт с размером сети, что
указывает на задержку памяти (гипотеза, без аппаратных счётчиков). RAM не ограничение.

**Q9. Удалось ли запустить все 139,255 нейронов?**
Да, 14,259,157 рёбер в симуляции:

- калибровка 19 gain × 3 seed;
- режим на baseline;
- эквивалентность;
- 60 изолированных прогонов smoke test на 4 backend;
- проба с выключением входа.

**Q10. Какой measured RAM полного коннектома?**
Peak RSS процесса симуляции: compiled TS — 268–321 MiB, compiled ED — 273–327 MiB, NumPy TS — 229–388 MiB,
NumPy ED — 235–404 MiB. Сборка сети — 935 MiB. Компоненты — в разделе MEMORY.

**Q11. Какова активность полного коннектома?**
На baseline gain 0.115:

| вход | частота популяции | активных за 1 с | молчащих | рефрактерность |
|---|---|---|---|---|
| 0.001 % | 6.2 Гц | — | — | — |
| 0.01 % | 8.0 Гц | 23–29 % | 71–77 % | 0.8–1.5 % |
| 0.1 % | 10.6 Гц | 44–46 % | 54–56 % | 1.6–2.0 % |
| 1 % | 14.1 Гц | 76–78 % | 22–24 % | 2.2–2.4 % |

Кроме того: 142–200 событий на спайк, 45k–119k уникальных целей за шаг, 2.8·10⁸ событий в секунду модели при

**Q12. Есть ли self-sustained activity?**
Да.

- На baseline — во всех 3 seed калибровочной пробы.
- В пробе 500 + 500 мс активность после выключения входа держится на 4–10.5 Гц и ни разу не падает до нуля во
  всех 9 прогонах.

Это самоподдерживающаяся рекуррентная активность модели, не память.

**Q13. Насколько ошибся full-connectome ESTIMATE из M2?**

- **RAM:** 206 MiB против 247 MiB, −17 %.
- **Время NumPy по модели M2** при фактических событиях: медианная ошибка 7.8 %, максимальная 25 %.
- **Сценарный расчёт:** 0.78 с против 1.09 с на секунду модели при ~1 % спайков, −28 %. Главная причина:
  предполагалось 102 события на спайк, а активные нейроны имеют больше выходов (142–180).
- **Собственная ESTIMATE M2.5 до запуска:** по RAM ошиблась на −1.5 %. Модель стоимости, по которой она
  строилась, занизила время compiled на полном мозге на 35–39 %.

**Q14. Имеет ли смысл дальше оптимизировать event-driven CPU backend?**
Как основное направление — нет. В клетках исхода C compiled ED в 1.6–2 раза медленнее compiled TS, а предел
любой ED-реализации на этой связности — 1.1–1.9× над time-step на 50k и полном мозге (до 2.9× на 10k при 0.1 %). Имеет смысл только для очень разреженных
режимов (≤ 0.01 % входа в сетях без самоподдержания, где выигрыш уже 3–28×). Больший потенциал у оптимизаций
доставки событий, общих для обоих режимов.

**Q15. Что разумнее: M3 plasticity или ещё один performance backend?**
**M3 plasticity** с compiled time-step как основным движком. Производительности хватает (полный мозг —
0.23–1.3 с на секунду модели, ≤ 0.33 GiB). Главная стоимость — события, и другой CPU-backend её принципиально не
уберёт. Решение о новом backend (многопоточность, GPU, нейроморфное железо) имеет смысл принимать после M3, когда
станет известна стоимость правила пластичности на событие.
